# 双模型查询与交付复核（2026-11-24）

结论：**不通过端到端隔离验收**。查询执行和结果模型调用有成功审计，
但脱敏 MCP 回执没有阻断消息历史等旁路。本文不包含业务结果或凭据。

## 本轮证据与边界

服务端校验、SELECT 和 QueryPlan 执行审计对应同一个真人 Union ID、应用、
会话和 turn。校验与 SELECT 使用的凭据归属 Union ID、邮箱均与各自审计一致。
观察到一次 SELECT 成功，返回 11 行、未截断；计划执行记录为 single、
run_index=1、max_runs=1。没有观察到重复查库证据。此处没有重跑 SQL。

结果代理审计记录实际请求与响应模型均为 Qwen/Qwen3.8-27B-FP8、HTTP 200、
11,580 ms、一次请求、零网络重试、零纠错。旧审计没有保存实际 token 上限、
thinking、temperature、finish_reason 和内部 tool-call 参数，因此不能用
部署默认值补作这次请求的实测证据。

这些证据不能独立证明 Gateway 最初的真人映射、数据库授权全集、源表粒度、
刷新完整性、会话时区或 Decimal 的全链路生产保真。已有合成链路验证应与
真实业务审计区分。第三条消息目前为已撤回状态，无法据此判定其原始用途。

## Findings

1. **P1：结果可经其他读取通道回到编排模型。** 工具不返回 rows，但编排
   模型通过 history 回读结果卡，已经破坏文档约定的隔离。当前插件直接调用
   botmux send；宿主 history/quoted 的全文、原始卡片和附件读取没有结果
   分类拦截。托管 lark-cli、转发、其他身份及文件访问还需逐项检查。
   此问题尚未修复，禁止描述为“端到端隔离已通过”。
2. **P2：交付责任和技能契约冲突。** 结果插件已投递，旧技能仍要求主模型
   发送 final_markdown，导致追加重复摘要。0.4.21 删除旧交接指导并增加
   complete-without-resending 回执指令；这能修正正常流程，但不是对任意
   主模型发送行为的宿主级强制防重复。
3. **P2：展示格式和口径重复。** 模型口径与底部确定性口径重复；工具缺少
   小数位/千分位参数。0.4.21 将口径归渲染层统一负责，支持 table_formats
   的精确定点展示，包括大于 2^53 的金额和负数，源值不变。
4. **P2：投递缺少可关联的安全回执。** 旧回执只含状态/计数，促使调用方
   回读业务正文验收。0.4.21 返回 deliveryId、主消息及附件消息 ID；新增
   get_query_delivery_status_for_user，无参数、按可信真人/应用/会话和
   当前结果版本查询审计中的回执。它不调用 SQL 或模型，不返回正文、列名、
   文件名或路径。pending/unknown 不是重新投递许可；窗口中无记录或损坏
   时返回未知/不可用，不伪称成功。
   独立复核发现并修正了两类状态问题：部分投递结束后永久 pending，改为
   unknown 并保留已确认消息 ID；清理后 version 从 1 重用会匹配旧回执，
   改为同时绑定随机 generationId 与 version。首轮、追问、覆盖、touch 和
   清理的迟到请求也携带代次守卫，避免旧请求误操作清理后重建的新结果。
5. **P2：混合粒度的自动统计可能误导分析。** 返回结果包含合计和明细时，
   对全部行再求和不是业务合计。0.4.21 明示自动统计覆盖全部返回行，并
   提供 claims.row_indices，让模型调用精确工具时选择同粒度明细或引用
   已有合计。不会根据“合计”等业务文案猜测并删除原始行。自由分析仍是
   模型生成，不能因表格准确就声称所有推断正确。
6. **P1（合成异常场景）：绑定失败后仍会执行无绑定查询。** 旧代码在缺少
   绑定密钥或预留结果槽位失败时批量清理结果后继续查数。0.4.21 改为查询前
   返回 result_binding_unavailable；无法建立身份绑定时不清理其它结果。
   配额不足时仅按捕获的旧代次失效当前调用者的旧绑定，防止新请求失败后
   追问误用旧结果，不删除其他调用者或并发新代次。缺密钥与低配额都使用
   本地合成服务回归；这不是本次业务查询的已发故障。

## 宿主修复边界

宿主应建立通用的受保护结果来源记录与脱敏投递查询，而不是为权限表、
元数据表、业务表分别开发交付链路。首轮与追问共用结果绑定、产物和投递边界。

保护记录应包含 delivery ID、可信身份/应用/会话/turn、结果 generation、
provider 消息及资源 ID。provider 已接受但 ACK 丢失时必须保留“不确定”状态，
在来源无法确认时阻断读取和重复交付，不能因超时删记录后放行。跨应用读取、
嵌套转发、原始卡片、自动上下文、附件下载和本地结果文件都属于验收面。

只过滤 history 不足以实现硬隔离。如果编排进程仍能获得原始 IM 凭据、读取
私有结果目录或调用不受控 API，必须由宿主的受限工具/凭据代理和沙箱策略
收口；不能把“请勿读取”的提示词当作权限控制。现有业务内容已经进入外部
上下文的会话也不能通过热改配置清除历史上下文，切换后需要新建干净会话。

## 版本与验收

当前核对的已部署基线：BotMux e3ac534ee、插件 0.4.20（源提交 f553dd3）、
Python 服务 0.4.5。0.4.21 是本次候选改动，发布和实际安装结果须另行记录。
未核验其他版本组合，不构造“兼容最新版”的承诺。

验收先用纯合成数据：工具注册、真人可信身份、单次查询、模型真实响应、
明细/内联图/文件、脱敏回执、跨通道负向读取、取消/版本替换/不确定 ACK、
只交付一套结果。最后才在同一权限与可信边界下做一次小范围真人验收。
不得由编排模型回读业务正文、重跑业务查询或用历史模型探针代替验收。
